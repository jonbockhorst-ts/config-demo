# ESO Config Demo

Local end-to-end prototype for this configuration flow:

`GitHub -> Argo CD -> Helm -> ConfigMap + ExternalSecret -> generated Kubernetes Secret -> mounted files -> .NET app`

The prototype proves:

- non-secret per-environment config lives in Git and is rendered into `appsettings.global.json`
- secret material is resolved by External Secrets Operator and rendered into `appsettings.secrets.json`
- the app uses normal .NET config loading and does not call AWS Secrets Manager at startup
- fixed file paths replace env-suffixed mounted config files
- no chart feature flags are required for the steady-state file model

## Local demo shape

- `app/`: minimal ASP.NET app
- `charts/topstepx/`: shared chart, modeled after the real shared `topstepx` chart flow in Argo
- `envs/demo/`: environment chart that depends on the shared `topstepx` chart
- `apps/demo.yaml`: Argo `Application`
- `scripts/`: local bootstrap helpers for `k3d`/`k3s`, Argo CD, ESO, and seed secrets

## Config layering

At runtime the app loads:

1. `/app/appsettings.json`
2. `/app/appsettings.global.json`
3. `/app/secrets/appsettings.secrets.json`
4. environment variables

## Local secret source

The local prototype uses ESO's Kubernetes provider, not AWS Secrets Manager.

The bootstrap script seeds Kubernetes Secrets into the `eso-seed` namespace, and the chart's
`SecretStore` lets ESO read those secrets and generate the application-facing
`appsettings.secrets.json` file in the `demo` namespace.

That means the local `remoteKey` values refer to Kubernetes Secret names, for example:

- `databases-postgres-demo`
- `auth-jwt-demo`

In the real AWS-backed implementation these would become resource-shaped AWS SM paths such as:

- `/databases/postgres/demo`
- `/auth/jwt/demo`

## Chart behavior

- `appsettings.global.json` always renders from Git-tracked Helm values
- `appsettings.secrets.json` is generated by ESO from the `secrets` bindings in values
- the shared chart owns the final JSON shape
- there are no `useAppsettings*` feature flags in the chart API

## Prerequisites

- Docker
- `k3d`
- `kubectl`
- `helm`
- access to a GitHub repo that contains this project

## Bootstrap

Set the GitHub repo URL that Argo should watch, then run:

```bash
export REPO_URL="https://github.com/<org-or-user>/eso-config-demo.git"
./scripts/bootstrap-demo.sh
```

The scripts pin all `kubectl` and `helm` operations to the dedicated local context
`k3d-eso-config-demo` by default, so they do not use whatever your current ambient
`kubectl` context happens to be.

After bootstrap:

- Argo CD runs in `argocd`
- ESO runs in `external-secrets-system`
- the demo app runs in `demo`

Useful checks:

```bash
kubectl --context k3d-eso-config-demo get applications -n argocd
kubectl --context k3d-eso-config-demo get externalsecret -n demo
kubectl --context k3d-eso-config-demo get secret appsettings-secrets -n demo -o jsonpath='{.data.appsettings\.secrets\.json}' | base64 -d
kubectl --context k3d-eso-config-demo get configmap appsettings-global -n demo -o jsonpath='{.data.appsettings\.global\.json}'
kubectl --context k3d-eso-config-demo logs deploy/demo-app -n demo
```
