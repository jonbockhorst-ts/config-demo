# ESO Config Demo

Local end-to-end prototype for this configuration flow:

`GitHub -> Argo CD -> Helm -> ConfigMap + ExternalSecret -> generated Kubernetes Secret -> mounted files -> .NET app`

The prototype proves:

- non-secret per-environment config lives in Git and is rendered into `appsettings.global.json`
- secret material is resolved by External Secrets Operator and rendered into `appsettings.secrets.json`
- the app uses normal .NET config loading and does not call AWS Secrets Manager at startup
- fixed file paths replace env-suffixed mounted config files
- no chart feature flags are required for the steady-state file model
- mixed sections like `Temporal`, `MarketDataApi`, and `Strapi` can be split cleanly between non-secret and secret fields

## Local demo shape

- `app/`: minimal ASP.NET app
- `charts/topstepx/`: shared chart, modeled after the real shared `topstepx` chart flow in Argo
- `envs/demo/`: environment chart that uses the app default for one setting
- `envs/demo-override/`: environment chart that overrides that same setting
- `apps/*.yaml`: Argo `Application` manifests for both demo environments
- `scripts/`: local bootstrap helpers for `k3d`/`k3s`, Argo CD, ESO, and seed secrets

## Config layering

At runtime the app loads:

1. `/app/appsettings.json`
2. `/app/appsettings.global.json`
3. `/app/secrets/appsettings.secrets.json`
4. environment variables

## Local secret source

The local prototype uses ESO's Kubernetes provider, not AWS Secrets Manager.

The bootstrap script seeds Kubernetes Secrets into the `eso-seed` namespace, and the chart's
`SecretStore` lets ESO read those secrets and generate the application-facing
`appsettings.secrets.json` file in the `demo` namespace.

That means the local `remoteKey` values refer to Kubernetes Secret names, for example:

- `databases-postgres-demo`
- `temporal-demo`
- `api-marketdata-demo`
- `auth-jwt-demo`

In the real AWS-backed implementation these would become resource-shaped AWS SM paths such as:

- `/databases/postgres/demo`
- `/temporal/demo`
- `/apis/marketdata/demo`
- `/auth/jwt/demo`

## Chart behavior

- `appsettings.global.json` always renders from Git-tracked Helm values
- `appsettings.global.json` is a direct JSON rendering of the `appsettings` values tree
- `appsettings.secrets.json` is generated by ESO from two values-driven inputs:
  - `secrets.template`: the app-facing JSON shape with ESO placeholders
  - `secrets.vars`: the variable map that defines `remoteKey`/`property` bindings
- the shared chart owns the final JSON shape
- there are no `useAppsettings*` feature flags in the chart API
- values naming:
  - `appsettings`: non-secret config rendered into `appsettings.global.json`
  - `secrets.template`: the app-facing secret JSON structure
  - `secrets.vars`: ESO variable definitions

## Prerequisites

- Docker
- `k3d`
- `kubectl`
- `helm`
- access to a GitHub repo that contains this project

## Bootstrap

Set the GitHub repo URL that Argo should watch, then run:

```bash
export REPO_URL="https://github.com/<org-or-user>/eso-config-demo.git"
./scripts/bootstrap-demo.sh
```

The scripts pin all `kubectl` and `helm` operations to the dedicated local context
`k3d-eso-config-demo` by default, so they do not use whatever your current ambient
`kubectl` context happens to be.

After bootstrap:

- Argo CD runs in `argocd`
- ESO runs in `external-secrets-system`
- the base demo app runs in `demo`
- the override demo app runs in `demo-override`

## Realistic split example

The app carries a default in [app/appsettings.json](/Users/jonbockhorst/dev/config-demo/app/appsettings.json:1):

```json
"HedgeDetection": {
  "ImmediateEnforcementThreshold": 8
}
```

The shared chart also carries some dev-wide non-secret defaults in [charts/topstepx/values.yaml](/Users/jonbockhorst/dev/config-demo/charts/topstepx/values.yaml:1), for example:

```yaml
appsettings:
  FeatureFlags:
    AllowAnonymousRegistration: false
    EnableHubspotEmails: false
  Temporal:
    Address: topstepx-dev.tmprl.cloud:7233
    Namespace: topstepx-dev
    TaskQueues:
      - topstepx-temporal-worker-queue
  MarketDataApi:
    BaseUrl: http://webapi.marketdata.svc.cluster.local
    EventHubUrl: http://webapi.marketdata.svc.cluster.local/hubs/event
  Strapi:
    BaseUrl: https://strapi-cms.topstep.com/api/
  ElasticSearch:
    Url: https://topstepx.es.us-east-2.aws.elastic-cloud.com/
    Username: elastic
    CloudId: topstepx-demo:ZXMtdXM...==
```

Both demo environments inherit those values unless they explicitly override them. This mirrors the real TopstepX shape where a section like `Temporal` has both non-secret and secret siblings:

- `appsettings.Temporal.Address`
- `appsettings.Temporal.Namespace`
- `appsettings.Temporal.TaskQueues`
- `secrets.Temporal.ApiKey`

and a section like `ElasticSearch` can share one secret source for multiple secret leaves:

- `appsettings.ElasticSearch.Url`
- `appsettings.ElasticSearch.Username`
- `appsettings.ElasticSearch.CloudId`
- `secrets.ElasticSearch.remoteKey`
- `secrets.ElasticSearch.Password.property`
- `secrets.ElasticSearch.CloudApiKey.property`

The `demo` environment does not set `HedgeDetection.ImmediateEnforcementThreshold` in Helm values, so the app keeps the base value `8`.

The `demo-override` environment sets this in [envs/demo-override/values.yaml](/Users/jonbockhorst/dev/config-demo/envs/demo-override/values.yaml:1):

```yaml
appsettings:
  HedgeDetection:
    ImmediateEnforcementThreshold: 12
```

The shared chart renders `appsettings` directly to `appsettings.global.json`, so the two environments prove:

- app default only: `demo` -> `8`
- env override: `demo-override` -> `12`
- shared dev global defaults: both envs inherit the same `FeatureFlags` section from the shared chart values

The shared chart also shows the comparison shape where the secret JSON structure lives in values:

```yaml
secrets:
  template:
    Jwt:
      Secret: "{{ .jwtSecret }}"
    ElasticSearch:
      Password: "{{ .elasticSearchPassword }}"
      CloudApiKey: "{{ .elasticSearchCloudApiKey }}"
  vars:
    jwtSecret:
      remoteKey: /auth/jwt/dev
      property: secret
    elasticSearchPassword:
      remoteKey: /elasticsearch/topstepx
      property: password
    elasticSearchCloudApiKey:
      remoteKey: /elasticsearch/topstepx
      property: cloudApiKey
```

In the local demo, those `remoteKey` values point to Kubernetes Secrets in `eso-seed`, but the structure is meant to map directly to AWS Secrets Manager later.

Useful checks:

```bash
kubectl --context k3d-eso-config-demo get applications -n argocd
kubectl --context k3d-eso-config-demo get externalsecret -n demo
kubectl --context k3d-eso-config-demo get externalsecret -n demo-override
kubectl --context k3d-eso-config-demo get secret appsettings-secrets -n demo -o jsonpath='{.data.appsettings\.secrets\.json}' | base64 -d
kubectl --context k3d-eso-config-demo get configmap appsettings-global -n demo -o jsonpath='{.data.appsettings\.global\.json}'
kubectl --context k3d-eso-config-demo get configmap appsettings-global -n demo-override -o jsonpath='{.data.appsettings\.global\.json}'
kubectl --context k3d-eso-config-demo logs deploy/demo-app -n demo
kubectl --context k3d-eso-config-demo logs deploy/demo-app -n demo-override
```
